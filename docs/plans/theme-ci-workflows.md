# 主题 CI 可复用工作流方案

本方案面向插件与各主题仓库的维护者：把参考主题已验证的构建、晋升、打包流程收进本仓库，作为可复用工作流和 CLI 能力提供给所有接入主题，各主题只保留触发入口与版本配置。

本文是待批准方案，尚未实施。实施涉及本仓库发版和多个主题仓库的发布链路，按下文各步骤的批准点推进。

## 背景与目标

参考主题的流程是标准流程，其余主题将改为同一流程：开发分支推送后，CI 把 Demo 分支与开发源码合并进候选分支并重建生产资源；人工审阅候选后，晋升工作流快进到 Demo 分支并要求重建无差异；版本 tag 触发打包并校验包内容。生成文件冲突由合并步骤自动处理，源码冲突使构建失败。该流程已在参考主题的真实运行中验证，实现与验证记录保存在其私有仓库。下文「参考主题」指首个采用标准流程的私有主题仓库，「验证主题」指工作区中专门用于验证新公共能力的主题。

现状问题：

- 生成文件的判定写在参考主题的合并脚本里，复制了本插件的输出命名；插件命名一变，各主题脚本都要同步。
- 其他主题的构建工作流各自演化，合并策略、凭据与插件来源都不同，同样会遇到生成文件冲突。
- 流程改进要逐个仓库复制，无法保证一致。

目标：生成文件判定只存在于本插件；流程只维护一份；主题接入只需调用入口、固定版本与凭据。

## 设计选择

**合并能力放进 CLI。** 新增 `merge` 子命令，按插件实际输出命名和 Mixer snippet 配置识别生成文件：只涉及生成文件的冲突按候选侧解决，其余冲突列出并失败，合并前即失败的 Git 错误原样失败。它与现有的 build、package 等子命令一样，本地与任何 CI 均可运行。判定逻辑与 [输出命名](../../src/plugins/config.ts)、[Mixer 写出](../../src/plugins/mixer.ts) 同仓维护，修改任一处时必须同步复核 `merge` 的判定与测试。

**流程做成本仓库的可复用工作流。** 本仓库公开，跨组织的主题仓库可以直接调用；工具层仓库为私有，不能承载跨组织调用的工作流。可复用工作流内部通过 `$/` 自引用语法调用本仓库的复合 Action，解析到调用方所固定的同一提交（[GitHub 变更说明](https://github.blog/changelog/2026-07-30-reference-same-repository-actions-with-self-repository-syntax/)，2026-07-30 起正式可用，要求 runner 2.336.0 及以上；2026-10-05参考主题运行所用 runner 为 2.337.0）。

**插件版本只固定一处。** 调用方 `uses:` 的提交同时决定工作流与插件版本：复合 Action 从自身所在的仓库副本提供插件源码，不再按主题配置另行检出插件。主题的版本配置只保留工具层提交、Node 与 Shopify CLI 版本。

**主题差异只作为输入。** 主题显示名、分支名、产物名、工具层仓库与凭据作为输入或 secret 传入；工作流不含主题专属逻辑。各主题的触发、`concurrency` 与 `permissions` 留在调用文件中声明。

不采用的方案：

- 只发布复合 Action、各主题保留完整工作流：流程仍需逐仓复制，问题二、三不解决。
- 保留各主题自己的合并脚本：生成文件判定继续复制插件知识。
- 把工作流放在工具层仓库：私有仓库的可复用工作流不能被其他组织的主题仓库调用。
- 为其他主题保留 `main` 剔除 `.vitify` 的旧模型：与标准流程分叉，正是本方案要消除的差异。

## 实施步骤

### 1. CLI `merge` 子命令

在 [CLI 入口](../../src/cli.ts) 增加 `merge` 模式，参数为 `--path <theme>` 与按顺序合并的完整提交 SHA。依次合并，除最后一个外每次合并后提交，最后一次保持未提交以便构建产物进入同一合并提交；与参考主题脚本行为一致。处理过的生成文件路径输出到标准输出，并在存在 `GITHUB_STEP_SUMMARY` 时写入摘要。

实现参照参考主题已验证的合并脚本，判定改为读取运行时的 snippet 配置与插件命名规则。

依赖：工作区内未提交的 `package` 子命令改动先完成提交，避免 CLI 入口的并行修改冲突。

完成条件：在临时 Git 仓库复现参考主题已验证的场景集，结果一致：生成文件的内容、修改与删除、新增、生成范围内重命名冲突自动处理；布局、模板、手写资产、Demo 侧源码、生成与源码混合、重命名到源码路径的冲突失败；工作区脏导致的非冲突失败原样失败；两次合并后保留两个来源的祖先关系。另以参考主题曾导致构建中断的真实提交复现原 CSS 冲突并确认自动处理。

### 2. 复合 Action 与可复用工作流

依赖步骤 1。在本仓库新增：

| 文件                                   | 来源与职责                                                                                        |
| -------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `.github/actions/toolchain/action.yml` | 来自参考主题的工具链 Action：检出工具层、放置插件源码、安装 Vite+、冻结安装依赖、安装 Shopify CLI |
| `.github/workflows/theme-build.yml`    | 来自参考主题构建：合并、Theme Check、构建、提交候选、摘要与检查报告                               |
| `.github/workflows/theme-promote.yml`  | 来自参考主题晋升：候选仍为当前版本、快进、重建无差异、推送 Demo 分支                              |
| `.github/workflows/theme-package.yml`  | 来自参考主题打包：tag 校验、来源校验、打包、包内容校验、草稿 Release                              |

包内容校验优先并入 `package` 子命令；该子命令尚不覆盖的参考主题校验项（版本与 tag 一致、包内文件与跟踪文件逐项一致、开发文件排除）补进 CLI，不在工作流中另放脚本。插件源码从复合 Action 所在的仓库副本放入工具层 workspace 后再安装，安装后在 CI 中构建插件。

本仓库自身的 [CI](../../.github/workflows/ci.yml) 增加对新工作流文件的语法校验。

完成条件：用验证主题的调用文件跑通构建、晋升与打包各一次（工作区约定新公共能力先在验证主题验证）；构建摘要列出来源、Demo 与自动处理路径，晋升重建无差异，打包产出草稿 Release 且包校验通过。验证主题迁移到标准分支模型属于步骤 4 的一部分，在此提前进行。

### 3. 参考主题改用可复用工作流

依赖步骤 2 发版。参考主题的三个工作流改为调用文件，删除自有的合并脚本、工具链 Action 与包校验脚本，版本配置删去插件仓库与提交两项，调用文件固定本仓库提交。

完成条件：真实构建在无新源码时不产生新候选提交（重建无差异），摘要与报告齐全；晋升与打包至少各在下一次实际发布时验证。

### 4. 其他主题迁移

依赖步骤 3。按先验证主题、后关联发布主题的顺序逐个迁移其余主题，每个主题单独批准：

- 新建候选分支，复制调用文件与版本配置，配置工具层只读 Deploy Key，替换原有个人访问令牌。
- 删除旧的 `build-dev.yml`；`main` 改为只由晋升工作流写入。
- 首次晋升会把 `.vitify` 与工程文档带回 `main`。Shopify GitHub 集成对主题目录之外的文件只给出忽略警告，参考主题已按此运行；如需减少噪声，在 `.shopifyignore` 中排除，但它只作用于 Shopify CLI，不消除集成警告。

关联发布主题的仓库，其 `main` 直接同步线上主题。切换时先停用旧工作流，再建立候选与首次晋升，避免两条流水线同时写入 `main`；首次晋升前审阅候选差异。

没有远程仓库的主题是否纳入，由维护者决定。

完成条件：每个主题完成一次真实构建与晋升，旧工作流已删除，`main` 的写入来源只有晋升工作流。

## 验证与恢复

本方案的必需证据：步骤 1 的临时仓库场景与参考主题真实提交复现；步骤 2 在验证主题的三条工作流真实运行；步骤 3、4 各主题的真实构建与晋升运行链接。

恢复：本仓库新增能力不改变现有子命令行为，发版后未迁移的主题不受影响。主题迁移以普通提交进行，撤回时恢复原工作流文件即可；候选分支保留，不删除远程历史。关联发布主题的仓库撤回需同时恢复旧工作流对 `main` 的写入方式，撤回前确认 `main` 未包含尚未审阅的候选内容。

## 实施前核对

执行前先验证：

- `$/` 自引用在被跨组织调用的可复用工作流中解析到本仓库被调用的提交，复合 Action 内可取得该仓库副本的完整源码以供 workspace 安装。
- 跨组织调用时 secret 必须由调用方显式传入；`secrets: inherit` 只在同一组织或企业内可用（[GitHub 文档](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)）。
- 各主题仓库的 Actions 设置允许调用外部工作流；2026-10-05 查询参考主题与现有接入主题均为允许全部 Action，迁移时复查。
- 工作区未提交的 `package` 子命令改动的最终行为，以确定包校验的合并方式。

任一项不成立时先调整设计并更新本文，不带着未验证前提实施。

## 公开范围

本仓库公开。本文与可复用工作流只出现仓库名称和凭据的 secret 名称，不写入任何凭据值；工作流输入不得要求在调用文件中明文传入凭据。
